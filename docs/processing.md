# 処理の仕組み

## 方針

- 入力は S20 の生データフォルダーだけです（bag、`info/calibration.yaml`、PPK を使うなら `BASE.BIN`／`ROVER_PPKRAW.bin`）。メーカーソフト（PointClouds Studio）は使いません。
- CUDA と ROS には依存しません。重い処理は CPU（rayon）で並列化し、通り抜け判定のレーザー・通過物の判定・着色の z バッファは wgpu のコンピュートシェーダーで計算します（GPU がなければ CPU）。
- GNSS を使う最適化は、現場付近を原点とするローカル ENU で行います。

## クレートの構成

| クレート | 役割 |
|---|---|
| `s20-io` | bag、校正、データフォルダー、GNSS（ENU への変換、妥当性判定）、LAS／LAZ と Potree の読み書き |
| `s20-geom` | SO3／SE3、点群の前処理、ボクセル地図、VGICP、軌跡の補間 |
| `s20-lio` | オドメトリ |
| `s20-opt` | 軌跡の最適化 |
| `s20-ppk` | PPK 測位（RTKLIB demo5 を内蔵） |
| `s20-finish` | 点群生成（通り抜け判定、面への投影、通過物の判定）、着色 |
| `s20-visual` | 画像の姿勢合わせ、カメラの校正、COLMAP 出力 |
| `s20-pipeline` | 工程の組み立て（CLI と GUI が共用）、軌跡と ImgPose.txt の出力、進捗と中断 |
| `s20-cli` | コマンドライン（`s20`） |
| `s20-gui` | GUI（egui＋wgpu） |

## 1. 抽出

ROS1 bag v2.0 を直接読みます（非圧縮チャンク。末尾の壊れたバイトは無視します）。作業フォルダーの `data/` には点と画像を複製せず、bag の中の位置（スキャンごとの点の位置と点数、画像ごとの位置と長さ）と、IMU・GNSS の表だけを書きます（10 分の撮影で 10 MB 前後）。後の工程は bag を読み込み専用でメモリーマップして読みます。

機体が撮影中に推定した軌跡（`frame_pose.txt`）も、プレビュー用に `data/device_pose.txt` に直します。時刻をセンサーの時計に移し、LiDAR の取り付けの傾き（y 軸まわり 25°。メーカーの仕様の「対地傾斜 25°」）を掛けます。

## 2. オドメトリ（LIO）

IMU 密結合の反復拡張カルマンフィルタです。位置合わせは small_gicp の VGICP を移植したものです。

- **重力で傾きを補正**（既定で有効）：LiDAR の位置合わせは地図に対する相対の姿勢しか決めないので、長い撮影では地図ごと少しずつ傾き、まっすぐ歩いても向きによって上り下りします。LIO が加速度から求めた鉛直の向きを毎スキャン観測し、傾きへの LiDAR の重みを下げます。97 分の屋外の撮影で、傾きは平均 3.2° → 0.17°、高さのずれは最大 35 m → 2.2 m になりました。加速度計のバイアスの初期値（`ba0`）は機体ごとの値で、既定は作者の S20 の推定値です。軌跡の最適化のログに推定値が出ます。
- **IMU との食い違いの検査**（NIS、既定 200、0 で無効）：位置合わせが誤った対応点に引っ張られると、その場で向きを変えただけなのに位置がずるっとずれ、そのまま地図に書き込んで戻れなくなります。補正が IMU の予測から大きく外れたら、予測の近くで対応点を探し直します。その場で旋回した場面で横に 3 m 跳んでいた撮影で、終点のずれが 10.5 m → 1 cm になりました。ほかの 5 本の撮影は悪化しませんでした。
- **方位を IMU に任せる区間**（手動指定）：丸い丘（同心円の園路や円形の柵）や特徴のない斜面では、LiDAR の位置合わせが方位を少しずつ一定の向きに引きずり、ジャイロのバイアスの推定まで狂わせます。数分ならジャイロのほうがずっと正確なので、その区間では方位とバイアスを LiDAR で更新しません。丘のある 30 分の撮影で、1800 秒時点の水平のずれが 19.1 m → 0.20 m になりました（PPK との比較）。

## 3. 軌跡の最適化

LIO の軌跡を初期値に、全体を 1 つの最適化で解きます。

- **状態**：LIO のスキャンの終端（約 0.1 秒刻み）ごとのノットに、姿勢・位置・速度・ジャイロと加速度のバイアス。ノットの間は IMU の積分で動きを表すので、点ごとの姿勢を補間なしで求められます。
- **拘束**：IMU 事前積分（Forster 形式、バイアスの一次補正）、バイアスのランダムウォーク、全点の面の整合（粗い面から細かい面へ 3 段、Cauchy の重み）、GNSS（RTK／PPK。妥当性判定と誤 FIX の検出つき、Huber の重み）、ループ、最初のノットのゲージ。
- **ループ**：2 時刻の周りの局所地図を VGICP で位置合わせして相対姿勢を測ります（初期値を複数試し、点の一致率と収束先の一致で判定）。まずオドメトリの相対姿勢とループだけのポーズグラフでずれを軌跡全体に配り、その後で IMU と面の段で仕上げます。
- **再訪**（処理設定で選んだとき）：同じセッションの後の通過や別のセッションで同じ場所を通ったところを自動で見つけ、拘束にします。軌跡を 15 秒ごとの部分地図に切り、中心が 20 m 以内の組を位置合わせします。点の重なりが 2 割以上で、初期値を変えても同じ所に収束するものを採ります。重みは位置合わせの情報行列から決めます。壁や角で決まる方向は強く、生け垣や道に沿う方向は弱くします。道に沿う方向がほとんど決まらない組（道沿い）は、全体の重みも下げます。再訪と指定したループには Cauchy の重みをかけるので、食い違うものはあまり引きません。面の段の間で、その時点の軌跡で探し直します。
  - 建物の壁のように面のある場所では、離れた通過どうしでも数 cm で合います。GNSS のない 3 セッションの公園の撮影では、壁の二重（約 0.6 m）が 2〜4 cm になりました。
  - 林の中の小道のように、道沿いの組しかない場所では、数十 cm のずれが残ることがあります。どの組も道に沿って滑るうえ、回転や道を横切る方向も 0.2〜0.3 m・0.2〜0.5° ばらつくためです。屋外では GNSS の FIX で押さえるのが確実です。再訪は、FIX が切れる建物の脇や木の下で点群どうしを合わせる役になります。
- **GNSS があるとき**は、ループを測る前にポーズグラフの段で LIO を測位に引き寄せます。ドリフトした区間でループを測ると、正しい測位から離れた位置でループが固定されるためです。
- **誤 FIX の検出**：測位と LIO のアンテナ位置の差が、連続する測位の間で段差（既定で水平 15 cm・鉛直 30 cm 以上）になった区間を除きます。LIO が乱れている時刻の段差は LIO の跳びとみなします。段差の後に元の水準へ戻る区間、または欠測のあとに始まった側を誤りとします。
- **Huber の重み**は、大きく外れた測位でも一定の力で引き寄せます。Cauchy の重みでは、ドリフトした軌跡から離れた正しい測位を捨ててしまい、始点と終点の区間が 2.9 m ずれたまま「始点＝終点」のループで閉じて、建物が二重になった例がありました。
- **解き方**：面の重心が点と一緒に動く効果（同じ面を見るノット同士の結合）を、面ごとの低ランク項として扱い、三重対角の分解を前処理にした共役勾配法で解きます。ステップはコストが下がるときだけ受け入れます（LM）。

## 4. 点群生成

屋内・屋外で同じ設定です。

1. 点ごとの時刻の姿勢で置いた全観測から、5 mm の格子ごとに中心に最も近い実測点を代表点にします（重心は作りません）。
2. **通り抜け判定**：ボクセルを素通りしたスキャンが、点を測ったスキャンより多い所の点を消します。2 cm（いろいろな向きから多くのスキャンが測った細い物は守る）と 1 cm の両方で数え、どちらかで空きなら消します。鏡像・動いた物・植木のもや・細い物の周りの混ざった点が消え、細い物は残ります。
3. **孤立点の除去**：測距の 1.5%（最低 15 mm）以内にほかの観測がない点を消します。
4. **面への投影**：1 cm セルの全観測のモーメントで半径 8 cm の面を当て、法線方向に寄せます。遠くで測った点は、測距の見込み誤差に応じて寄せる範囲を広げます。
5. 寄せた後の位置で 5 mm に 1 点に間引きます。LAS 1.4／LAZ に面の法線つきで出します。
6. **通過物の判定**：面にならなかった点を、スキャンごとに点の方向の 0.8° の円錐の中のレーザーで調べ、少しの間（20 スキャン以下・2 秒以内）だけ測られて多くのスキャンに見通された点（通った車・人）を消します。

点群生成と着色は、空間の正方形（50 m、多ければ 4 分割）ごとに一時ファイルを使って行います。結果は一度に処理したときと点・色まで同じです。メモリはデータの長さやセッション数に比例しません。7350 万観測・出力 5500 万点の屋外の撮影で、点群生成 7.8 GB・約 9 分、着色 7.0 GB・約 12 分でした。メモリに余裕があれば、詳細パラメータの着色の `tile_size` を 0 にすると速くなります。

## 5. 軌跡・画像姿勢の出力

trajectory.txt（PointClouds Studio と同じ形式）、100 Hz の TUM、trajectory.las（GPS 時刻つき）とその 8 分木、着色に使う ImgPose.txt を出します。

## 6. 画像の姿勢合わせ

軌跡からそのまま求めた画像の姿勢には、わずかなずれ（時刻、取り付け、軌跡の誤差）が残り、着色が二重になったりぼけたりします。画像ごとに、カメラの姿勢を小さく回転・移動して、点群に結び付けた特徴点が、連続する画像・左右同時の画像・数秒離れた画像の間で合うようにします。

- 特徴点（SIFT）を照合し、光線と点群の局所平面の交点で点群に結び付けます。遮られた面に当たった対応は z バッファで外します。
- ソフト L1 の重みのガウス・ニュートン法で、6×6 ブロックの正規方程式を共役勾配法で解きます。補正は小さく保つ事前分布と、同じカメラの連続する画像のなめらかさで安定させます。
- 軌跡と点群は動かしません。結果は着色と COLMAP 出力に使います。

### 機体の校正

メーカーの校正ファイル（出荷時の `calibration.yaml`）のままでは、カメラの取り付けと魚眼のわずかな不整合が、撮影全体に共通の二重化として残ることがあります。同じ機体の処理済みの撮影を何本か使い、画像ごとの姿勢と一緒に、左右のカメラの取り付け（回転・位置）・魚眼の角度・主点を求め直します（「ツール」→「機体の校正」、`s20 calibrate-device`）。

- 推定に使っていない撮影でも、左右の整合・同じカメラの時間差の整合・着色の鮮鋭度が上がることを確かめました。
- 屋外と屋内（近距離）の撮影を両方含めて求めます。取り付け位置の数 mm の差は、遠くを写す屋外では写りにほとんど影響せず決まりませんが、1〜2 m を写す屋内では二重像として出ます。
- 各撮影の処理では校正を固定し、画像ごとの姿勢合わせだけを行います。

## 7. 着色

- 点ごとに写る画像を、距離・入射角・光軸からの角度・機体の回転の速さで点数付けします。
- 画像ごと・色ごとの露出の利得を重なりから求め、前後 60 秒の画像の利得の平均で割って掛けます（隣の画像との段差と左右のカメラの差だけを直し、日向・木陰の明るさは写真のまま）。
- 近い画像を暗い順に並べて 3 分の 1 の位置の画像を基準に、色がかけ離れた画像（撮影者の影、窓の反射、映り込み、白飛び）の点数を下げます。
- 2 帯域で混ぜます。細部は上位 3 枚から、5 cm のセルの色は候補 8 枚から点数の重みで混ぜ、画像ごとのホワイトバランスや露出の違いによる区画状の色むらを消します。
- 隠れの判定はセルの z バッファで、浅い角度で見る面（遠くの地面）は隣のセルの距離の傾きの分だけ許します。カメラから 40 m まで。どの画像にも写らない点は出力しません。

## 8. Potree の 8 分木

点群を書いたあと、Potree 2.0 の 8 分木を、PotreeConverter と同じ名前（`<点群のファイル名>_converted/` に `metadata.json`、`hierarchy.bin`、`octree.bin`）で横に書きます。Potree のビューアーでそのまま見られ、アプリの出力点群のプレビューもこれを読みます。

- 中身は位置・反射強度・色。圧縮は BROTLI で、約 1 億点の着色済み点群で 829 MB（1 点 8.4 B）、作るのに約 40 秒。
- PotreeConverter の既定（poisson）と同じく、各ノードはノードの中心に近い順に、取った点から間隔（立方体の 1/128）以上離れた点だけを取ります。Potree 本体のデコーダーで読み、元の点群と位置・色・反射強度まで一致することを確かめました。
- `metadata.json` の `s20` に元の点群のファイル名・大きさ・更新時刻を入れ、古くなったかを見分けます（Potree のビューアーは読み飛ばします）。
- Potree のビューアーは `file://` では読めないので、簡単な Web サーバーか PotreeDesktop で開いてください。

## 座標系

GNSS の緯度・経度・楕円体高を WGS84 の地球中心直交座標（ECEF）へ変換し、現場の原点で東・北・上（ENU）に回転します。単位は m です。

- 原点は、最初の妥当な RTK FIX、または条件を満たす PPK 測位の位置です。一度決めた原点は、再最適化・RTK と PPK の切り替え・セッションの追加でも共通です。
- z は原点の接平面に垂直な位置で、標高ではありません。ジオイドモデル、標高への変換、測地系の変換は行いません。現場程度の広さを対象としています。
- 座標系は `data/coordinate_frame.json` に保存し、GNSS を使った結果は出力フォルダーにも `coordinate_frame.json` を出します。例：

  ```json
  { "type": "local_enu", "origin_llh": [35.0, 139.0, 50.0] }
  ```

  `origin_llh` は緯度・経度（度）・楕円体高（m）で、この情報から ECEF との剛体変換を復元できます。GNSS を使わない結果は `{"type":"local_slam"}` で、地理座標との対応を持ちません。
- 点群・軌跡・画像姿勢はローカル座標のままです。大きな投影座標を足し戻さないので、Potree でもメートル単位でそのまま表示できます。LAS への地理参照情報の埋め込みはしていないので、成果物を渡すときは JSON も一緒に渡してください。
